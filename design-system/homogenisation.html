À homogénéiser

Constats remontés en documentant les composants pour ce design-system — pas un audit de code. Pensés comme des points de départ pour une discussion avec l'équipe dev, pas comme un plan de refacto : le détail technique (fichiers, diffs) reste dans homogenization-candidates.md pour qui voudra creuser.

1. Composants « ByX » et « Statistics » recopiés entre admin et public

Effort faibleRisque faible — une trentaine de composants de répartition/graphique (ex. missions par domaine) existent en double, quasiment à l'identique, selon qu'on est côté admin ou côté public.

Piste : un seul composant, piloté par le contexte d'affichage, pourrait remplacer ces paires.

Effort moyenRisque moyen — les vues de synthèse (KPI) partagent la même structure visuelle admin/public, mais les indicateurs affichés diffèrent réellement selon le contexte.

Piste : mutualiser la structure commune (encadré + titre + grille), en laissant chaque contexte fournir ses propres indicateurs.

2. Badge « en ligne / hors ligne » recopié à plusieurs endroits

Effort faibleRisque faible — un composant partagé existe déjà pour ce badge, mais son affichage est recopié à la main à 3 endroits du produit plutôt que réutilisé.

3. Famille « pastille / badge / tag » fragmentée

Effort moyenRisque moyen — au moins 3 implémentations maison de ce pattern coexistent avec les composants DSFR équivalents (DsfrBadge/DsfrTag), sans qu'on sache toujours lequel utiliser dans du code neuf.

4. Blocs « dépliables » dupliqués par entité

Effort faibleRisque faible — deux familles de blocs dépliables (avertissements, modération IA) sont dupliquées presque à l'identique selon l'entité concernée (mission, organisation, territoire).

Ces blocs s'appuient sur un accordéon maison plutôt que sur l'accordéon DSFR — voir aussi la page Candidats migration DSFR.

5. Panneau de statistiques dupliqué (organisation / réseau)

Effort faibleRisque faible — quasiment identique des deux côtés ; seuls les champs d'API et les liens diffèrent.

6. Bloc d'informations dupliqué (mission / modèle de mission)

Effort moyenRisque moyen — les champs métier affichés diffèrent nettement selon le contexte ; seul l'en-tête (dates de création/mise à jour) semble mutualisable.

7. Un même patron « encadré + titre + liste de champs » recopié une dizaine de fois

Effort moyenRisque faible à moyen — même structure visuelle (encadré + titre + liste de champs) recopiée pour chaque entité du produit (activités, domaines, missions, modèles de mission, organisations, profils, réseaux, ressources, témoignages, territoires...), avec à chaque fois son propre contenu métier.

Piste : un bloc générique partagé (titre + encadré + liste), où chaque entité ne fournirait plus que ses champs.

8. Composants de saisie autocomplete non utilisés

Effort faibleRisque quasi nul — plusieurs composants de saisie autocomplete maison ne semblent plus utilisés nulle part (un import resté commenté faussait le comptage initial). Des équivalents DSFR (DsfrInputAutocomplete, DsfrSelectAutocomplete) sont déjà en place ailleurs.

À vérifier côté dev avant suppression — le fichier détaillé liste les composants concernés.

Incohérences de nommage

  • Trois préfixes concurrents pour un même concept — Base* (maison), Dsfr* (wrapper DSFR), Ui* (shadcn) — sans règle explicite sur lequel utiliser dans du code neuf (ex. Bouton : BaseButton / DsfrButton / UiButton).
  • Des regroupements au pluriel (« Badges ») et des composants au singulier (« Badge ») coexistent, sans que le nom relie visuellement les deux.
  • Rangement par type d'UI (composants de base / DSFR / UI) vs par domaine métier (sections, cartes...) coexistent sans règle, ce qui complique la détection de doublons.
  • Deux emplacements différents pour la même famille de composants selon le contexte admin/public — un emplacement unique éviterait la confusion structurelle.
