Bien prompter pour créer une page

Les pages de ce projet (design-system et prototypes) sont produites avec Claude. Ce guide réunit ce qui, en pratique, évite les allers-retours et les malentendus — pour que la première version soit la bonne, ou proche.

Avant de commencer

Ce dépôt est écrit et maintenu avec Claude. Pour créer un prototype ou une page de doc, dans l'ordre :

  1. Récupère le dépôt sur ton ordinateur. git clone https://github.com/ngouard5/jeveuxaider-design.git — ou, si tu ne connais pas git, le bouton vert Code › Download ZIP sur la page GitHub du dépôt.
  2. Ouvre ce dossier avec Claude. Avec Claude Code (terminal, commande claude dans le dossier) ou avec l'application Claude desktop (Cowork) en connectant ce dossier. Pas besoin de créer un Projet Claude ni de recopier des instructions à la main : Claude lit automatiquement AGENTS.md à la racine, qui donne le contexte du produit et pointe vers GUIDE-PROTOTYPAGE.md (pièges techniques à éviter) et prototype-starter.html (point de départ pour un nouveau prototype).
  3. Demande ce que tu veux, en suivant les règles ci-dessous.

1. Dis où ça doit vivre

design-system/prototypes/
Documente un composant existant : un bouton, un token de couleur, une règleTeste visuellement un parcours utilisateur complet, avec ses différents écrans et états

Nomme le fichier exact plutôt que « la page » ou « le prototype ». Par exemple : « Dans prototypes/verification-code.html, ajoute… » plutôt que « améliore la page de vérification ».

2. Appuie-toi sur le vrai code

Claude a un accès en lecture seule au code réel de l'application (le dossier jeveuxaider). Demande-lui explicitement de vérifier un champ, un libellé ou une couleur dans le vrai composant plutôt que de le laisser deviner.

Vérifie le vrai champ « pays de résidence » dans le formulaire d'inscription
réel avant de le maquetter (placeholder, valeur par défaut, composant utilisé).

3. Donne le contexte de l'écran

Pour un composant isolé, son nom suffit. Pour un écran, précise l'étape du parcours, le rôle concerné (bénévole, responsable d'organisation…) et l'état représenté (erreur, succès, chargement, vide).

4. Un prompt, un objectif

Plusieurs demandes ciblées valent mieux qu'une seule qui empile tout : plus faciles à vérifier, plus faciles à annuler si un point ne convient pas.

5. Pense aux deux bouts

Un défaut vu dans un prototype (hover manquant, couleur en dur) vient souvent d'un composant documenté ailleurs dans le design-system. Précise si le correctif doit aussi être répercuté dans sa doc.

Exemples

À préciserPlus efficace
« Redesign la page OTP »« Dans prototypes/verification-code.html, ajoute un état d'erreur et un état de succès au code de vérification »
« Corrige le hover »« Corrige le hover des DsfrButton : utilise --background-action-high-blue-france-hover, pas une couleur en dur »
« Fais un stepper »« Utilise le vrai fr-stepper du DSFR (voir dsfr.min.css), pas un composant maison »

Repères utiles

Le code réel de l'app (jeveuxaider) est en lecture seule : jamais de modification, uniquement une référence pour les bons champs, tokens et textes.

Les prototypes lient les vraies feuilles de style (compiled.css, dsfr.min.css) et réutilisent les vraies classes DSFR/JVA ; seuls le CSS de mise en page propre au prototype et le JS de démo restent embarqués — ce sont des maquettes interactives pour visualiser un parcours, pas du code de production.

Le design-system documente le composant réel tel qu'il existe ; pour un composant DSFR natif pas encore utilisé dans l'app, il est signalé explicitement comme non implémenté en prod (voir DsfrStepper).
